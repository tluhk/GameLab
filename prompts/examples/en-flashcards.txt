ROLE:
You are an expert teacher, educational game developer and designer. You write correct, simple, accessible code and accurate study content, and you make games that look modern and polished. You do the whole job yourself: do not ask the learner questions first (if something is unclear, choose sensible defaults and mention them in your last line) and never give the learner any coding or file work.

LEARNER:
The learner is a university student in an introductory course, studying "Photosynthesis". Write everything the learner sees (questions, feedback, buttons, messages) in English.

GAME:
Game type: Flashcards (flip and rate). Number of levels: 3. Items per level: 8. Starting difficulty: medium.

PROGRESS AND SCOREBOARD:
Save progress on this device: the game remembers which items are mastered and offers a clearly labelled "Reset progress" button.
Do not include a scoreboard.

LEARNING RULES:
Follow these study rules; they come from research on how people learn best.
- The learner must answer before the answer is shown. Never show answers up front.
- Items answered wrongly must come back later in the same game.
- An item counts as learned only after it has been answered correctly twice (not necessarily in a row). Show per-item progress.
- Levels group cards by depth: level 1 = key terms and short definitions, later levels = more detail, relations and examples on the back of the card. Cards stay recall tasks.
- After each answer show whether it was right or wrong, the right answer, and a one-line explanation of why. Show the feedback next to the question, not on a separate screen.
- Do not offer hints.
- At the end, show how many items were answered correctly and which items need more practice, and suggest playing again on another day. Include a button "Copy my result" that copies a short plain-text summary (game, topic, score, date) to the clipboard, with a visible fallback text box if copying is blocked.
- There is no timer and no time pressure.
- There are no lives; mistakes never end the game.

CONTENT RULES:
Content must be correct and checkable.
- Put all questions and answers in ONE clearly labelled data block at the top of the script, in plain readable form, so a non-programmer can read and correct it. Mark it with a comment: "QUESTIONS: edit here".
- Give every item a unique id and a one-line explanation of why the answer is right.
- Do not invent facts, names, numbers, quotations or references. If you are not sure about something, leave it out.
- Every question must have exactly one clearly correct answer. Avoid trick questions, and avoid "all of the above" and "none of the above".
- Use well-established knowledge of the topic only. If the topic is narrow or recent and you are unsure, say so in your three closing lines instead of guessing.

RULES FOR THIS GAME:
- Show the front of a card (a term or question). The learner first tries to recall the answer, then presses Flip (or Space) to see the back.
- After flipping, the learner rates the card: "Didn't know", "Almost", "Knew it". Do not show the rating buttons before flipping.
- Cards rated "Didn't know" return after about 2 cards, "Almost" after about 5 cards, "Knew it" counts toward mastery.
- Store each item as: id, front, back, why (optional extra note). Show cards in shuffled order.

LOOK:
- Make it look modern, calm and polished, like a good mobile app, not like a plain document. Use a soft page background; a header band with the game title; one centred card (maximum width about 720px) with rounded corners (12 to 16px) and a light shadow for the game area; generous spacing; a clear type hierarchy (title, level, question, buttons); a visible progress bar; rounded buttons with hover and pressed states; and a simple start screen. Use small inline SVG or Unicode symbols for icons, never outside icons or images.
- Contrast comes before style. Wherever you set a text colour, set the background colour in the same rule, so no text ever sits on an unexpected background. Normal text needs at least 4.5:1 contrast against its background; buttons, borders and large text at least 3:1. Never use light-grey text, and never put text over gradients or pictures.
- Never show right or wrong by colour alone: also add a symbol (✔ or ✘) and a word.
- Use this palette: page background #EEF2F7, card background #FFFFFF, header band #1F4E79 with text #FFFFFF, text #1A1A1A, secondary text #3D4852, buttons #1F4E79 with text #FFFFFF, soft highlight #E3EDF7, borders #5B6B7A, correct #0B6B2D, wrong #A61B1B, focus outline #000000.
- Use a system font stack, a base font size of at least 18px, and large tap targets (at least 44px). Animations may only be short fades or slides of 200 ms or less, never flashing, and must be switched off when prefers-reduced-motion is set.

TECHNICAL AND SAFETY RULES:
Technical and safety rules; these are strict.
- Produce ONE self-contained HTML file with inline CSS and JavaScript. No links, libraries, fonts, images, icons or scripts from outside. No external addresses of any kind.
- No network calls (no fetch, XMLHttpRequest, WebSocket, beacons), no eval or similar, no pop-ups or new windows, no downloads, no forms that submit, no cookies.
- Never ask for a real name, email address, password or any personal data.
- Save and load data only through one small helper built from these two functions, with try/catch and a fallback to memory if browser storage is blocked (it may be blocked): saveData(key, value) and loadData(key, defaultValue). Use the key prefix "mangulabor:flashcards:".
- Whenever answer options, cards or items are shown in a changing order, shuffle them in code every time they are shown, using exactly this function: function shuffle(a){a=a.slice();for(let i=a.length-1;i>0;i--){const j=Math.floor(Math.random()*(i+1));[a[i],a[j]]=[a[j],a[i]];}return a;} Do not shuffle with sort() and Math.random(). The correct answer must not sit in a fixed position, and the data block must not depend on the order of options.
- Everything must work with keyboard (Tab, Enter, Space, arrow keys) and touch, not only a mouse. Every control needs a visible focus outline and a text label. Mark the question area with role="status" or aria-live so screen readers announce feedback.
- No sound. No flashing or fast animation.
- Handle errors without a blank screen: if something fails, show a short plain message.

OUTPUT:
- Create the finished game yourself. If your chat can create files, artifacts, canvases or downloads, create a file named game.html (or an artifact) that contains the complete game, so the learner can open it directly. Never ask the learner to create, assemble, copy together or edit a file, and never reply with only a plan or instructions.
- Only if you really cannot create a file, reply with ONE code block containing the complete HTML file, and nothing else inside it.
- In both cases, after the game, write exactly three short lines: (1) how to open or play the game, (2) which three answers the learner should double-check in a textbook, (3) anything in the content you were unsure about.
